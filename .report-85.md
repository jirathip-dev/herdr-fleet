## Contract surface

- **RPC**: `queue.submit` (mutating, one approved submission) and
  `queue.status` (read-only, `params.submission_id` = `qs_` + 16 hex).
  Both ride the existing `hf-rpc-request/v1`/`hf-rpc-response/v1` envelope;
  unknown methods stay refused.
- **Schema**: v9, purely additive. `queue_ownership` carries
  `PRIMARY KEY (repository, issue_number)`: the database itself refuses a
  second live owner for one issue.
- **CLI**: `canter queue submit --request FILE --confirm-digest HEX64
  [--epoch N] [--grant REF=GRANT_ID]... [--resume INSTANCE=DIGEST]...
  [--host-available yes|no|unknown] [--harness-lanes N|unknown] [--caps
  G/R/H] [--idempotency-key IK] [--socket PATH] [--config PATH] [--json]` and
  `canter queue status --submission qs_...`. `--json` emits exactly one
  `hf-output/v1` envelope; the human surface carries the typed code.

## Acceptance points, each pinned by a named test

1. **Explicit approval binds the exact preview digest and selected scope;
   stale spec/epoch/config or revoked grant refuses before effects.**
   - `stale_digest_epoch_and_moved_revision_refuse_with_stable_codes`
     (digest mismatch → `refusal.plan.stale`; epoch mismatch →
     `refusal.state.epoch`; a moved role-config revision →
     `refusal.profile.revision` — all before any claim).
   - `wire_stale_digest_epoch_and_revision_refuse_without_claims` (the same
     three refusals over the real daemon socket: no `mutate.queue.submit`
     intent, no pending claim, no persisted row; only the subsequent clean
     submission persists exactly one submission row, run and ownership row).
   - `wire_revoked_grant_refuses_the_item_before_any_effect` (a revoked grant
     refuses the item `refusal.grant.inactive` with no run and no ownership row).
   - `revoked_grants_and_live_ownership_refuse_items`.
2. **Persist run membership and unique work ownership transactionally;
   double-click, retry and restart cannot duplicate owners or spawn effects.**
   - `submission_commits_membership_and_unique_ownership_transactionally`
     (membership rows, admitted runs and ownership rows in one transaction;
     a duplicate is refused `submission.already_owned`; the unique ownership
     row is proven).
   - `wire_double_click_replays_and_concurrent_retries_cannot_duplicate_owners`
     (sequential double-click replays the recorded response; a same key from
     a different request id is `state.claim_reused`; two REAL concurrent
     threads racing one request id + key produce exactly one owner — the
     loser replays or is refused the typed `state.claim_incomplete`, never a
     raw storage error; a later same-request retry replays).
   - `crash_before_commit_leaves_nothing_and_needs_a_fresh_key` and
     `crash_after_commit_keeps_exactly_the_committed_effects` (below).
3. **Partial admission is explicit per issue: admitted / waiting / refused;
   the submission is not claimed to be completed implementation.**
   - `wire_submit_partially_admits_and_status_reads_back_the_same_document`
     (a two-issue submission admits one, refuses the other with its reason
     code, and `admission {admitted, waiting, refused}` is rendered).
   - `capacity_holds_park_items_as_waiting_without_consuming_slots`
     (an exhausted axis holds the item `waiting` with the reused
     `refusal.admission.cap_*` code and consumes no slot).
   - `environment_holds_park_eligible_items_as_waiting`
     (`preview.host_unavailable` / `preview.occupancy_unknown` hold an
     eligible item as `waiting`, never as admitted).
4. **Only supported workflow steps execute; unsupported flows stay blocked
   and labelled, never stub success.**
   - `unsupported_or_unresolved_spines_refuse_the_whole_flow_labelled` and
     `wire_unsupported_step_is_refused_and_labelled_without_claims` (a step
     kind outside the closed `mutation::KIND_CAPABILITY` set, or a step whose
     capability the reviewed boundary does not carry, refuses
     `preview.step_unsupported` / `submission.boundary` before any effect).
5. **Paused fleets stay paused unless a separate explicit resume
   authorization is present; no implicit backlog expansion or main/release
   grant.**
   - `paused_runs_stay_paused_unless_explicitly_authorized` and
     `wire_paused_run_needs_the_explicit_resume_authorization` (an owned,
     paused run refuses `submission.paused` without an authorization; the
     presented authorization must verify against the durable resume digest;

6. **CLI/JSON and daemon readback agree; failure injection proves

## Transactional ownership evidence

- The ownership guarantee is enforced at THREE layers, all inside the one
  submission transaction that runs under the state guard: the live-ownership
  read (`owned.get(issue)` → `submission.already_owned`), the run-state
  fence (only a run that left the owned set frees its issue), and the
  `queue_ownership` primary key itself (a duplicate insert is a storage
  error the transaction rolls back).
- Concurrency evidence: two real client threads race the same
  `(request id, idempotency key)` against the running daemon
  (`wire_double_click_replays_and_concurrent_retries_cannot_duplicate_owners`).
  Exactly one transaction runs; the final durable state is asserted to hold
  one run for the raced issue and one ownership row per admitted issue.
- Retry/restart evidence: the sequential double-click returns the recorded
  response byte-for-byte; after both crash windows the durable state holds
  exactly the committed rows (`instances`/`queue_ownership` counts asserted
  after every scenario).
- A latent defect in the shared claim machinery was found by the concurrent
  probe and fixed: a same-request retry arriving while the first attempt was
  still `claimed` fell through to the INSERT and surfaced a raw SQLite
  UNIQUE error (`state.conflict`). The claim path now answers the typed
  `state.claim_incomplete` ("still in flight") and the concurrent test pins
  it (it rejects any other code).

## Failure injection — journal / restart reconciliation

Both windows use the daemon's crash-point hook in a real child process
(`CANTER_CRASH_POINT`), the same mechanism #74/#79 use:

- `crash_before_commit_leaves_nothing_and_needs_a_fresh_key` — the daemon is
  killed at `queue.after-intent` (the claim is journaled, the transaction has
  not started). A direct read of the state store shows no submission row, no
  run, no ownership; the restart resolves the claim (`doctor.pending_claims`
  = 0), the journal carries the `reconcile.queue.submit` record, the daemon
  log carries the reconciler's readback ("never committed"), a same-key
  retry is refused `state.ambiguous_claim`, and a fresh key then commits
  exactly one owner.
- `crash_after_commit_keeps_exactly_the_committed_effects` — the daemon is
  killed at `queue.after-commit` (the transaction committed, the response was
  never recorded). The committed submission row/items/runs/ownership are read
  back exactly, the restart resolves the claim, the journal and the daemon
  log carry the reconciler readback ("committed before the interrupt"), the
  restart `queue.status` readback returns the committed document, and a
  fresh-key resubmission refuses `submission.already_owned` — a restart never
  creates a second owner and never re-executes the submission.

## Not proven / deliberately out of this slice

- **Execution is not started here.** The submission commits membership and
  unique ownership; step execution and the role launch chain remain with the
  merged #73–#80 machinery and the #95/#96 continuation slices. "Admitted"
  means "the durable run exists and owns the issue", never "implemented".
- **The queue.submit reconciler is read-only by design.** It reads the
  commit marker, re-verifies the bound-input digest and reports; it never
  rewrites the claim and never re-executes. The claim resolves `ambiguous`
  through the shared claim machinery (a retry needs a fresh key), which is
  the merged doctrine for interrupted claims (`docs/contracts/spec-state.md`).
- **Occupancy/availability/credential attestations are caller-presented**
  and re-verified against durable state; they are never re-measured at
  submission time (probing a host would be an effect).
- **The `harness_lanes.unwrap_or(0)` gap in `admission_gate` (#48) is
  pre-existing and unfixed** — reported above, not patched.
