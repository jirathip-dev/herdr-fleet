### A2 shipped: native herdr lane-lifecycle registration (pi adapter)

- `src/adapters.rs`: when a pi profile operation runs inside a herdr pane
  (`HERDR_ENV=1` + `HERDR_PANE_ID` in the allowlisted environment), the
  adapter reports the lane through the workspace executable's documented
  custom-integration row (`herdr pane report-agent <pane> --source
  custom:herdr-fleet-pi --agent pi --state <state>`). Mapping from the
  typed-exit taxonomy: `start` succeeded -> `working`; terminal `prompt`
  (succeeded/failed/refused/ambiguous) -> `idle`; terminal `prompt` with
  `refusal.credentials` -> `blocked` + static message "harness credentials
  required" (never credential text). Reporting is a best-effort sideband
  (never changes the typed op result) and a no-op outside herdr.
- Wrapper/limitation note (exactly what needed a wrapper): `herdr agent
  start <NAME> --kind pi --pane <ID>` IS supported by herdr 0.8.2 (kind
  list includes pi — verified against the live CLI) but is pane-mediated:
  it starts an *interactive* agent in an existing pane at an interactive
  shell prompt and cannot be driven by a headless library adapter (the pi
  adapter launches pi as a direct argv one-shot child). The faithful
  adapter-mediated integration is herdr's documented custom-integration
  path (`pane report-agent` rows above; pi's own herdr hook,
  `~/.pi/agent/extensions/herdr-agent-state.ts`, is TUI-only and does not
  report headless `--print` runs). Releasing the source's authority
  (`herdr pane release-agent`, same `--source`/`--agent`) is the lane
  owner's pane-closeout step for future daemon wiring (no daemon caller
  exists in this bootstrap slice, so no speculative release call is wired;
  the row is documented in spec-capabilities.md).
- Contract tests (fake `herdr` logs the exact argv it receives to an
  allowlisted log path, so rows are pinned byte-for-byte):
  `pi_start_under_herdr_reports_working_with_the_documented_row`,
  `pi_prompt_under_herdr_reports_idle_after_a_successful_one_shot`,
  `pi_prompt_credentials_under_herdr_reports_blocked_with_a_static_message`,
  `pi_prompt_timeout_under_herdr_reports_idle_after_the_deadline_kill`,
  `pi_operations_outside_herdr_never_report_lifecycle` (no reports without
  the markers), `pi_herdr_report_failure_never_changes_the_typed_op_result`.
  Unit tests: `herdr_pane_context_requires_herdr_env_and_pane_id`,
  `herdr_lifecycle_report_maps_typed_results_to_semantic_states`.
- A2 live-herdr verification (isolated scratch pane, real daemon 0.8.2,
  2026-09-08; no fleet lane touched — scratch tab created in this lane's
  own workspace and closed afterwards):
  1. `herdr tab create --workspace w3D --cwd /tmp --label scratch-a2-33`
     -> scratch pane w3D:p2 (agent_status unknown before reporting).
  2. Adapter row `herdr pane report-agent w3D:p2 --source
     custom:herdr-fleet-pi --agent pi --state working` -> `herdr agent
     list`/`agent get` row: `{"agent":"pi","agent_status":"working"}`.
  3. Adapter row `... --state idle` -> agent row:
     `{"agent":"pi","agent_status":"done"}`; `herdr agent explain` reports
     semantic `state: idle` with the remote pi detection manifest
     (`remote/pi.toml`, fallback `default_known_agent_idle_fallback`) —
     herdr 0.8.2's agent-list API renders a custom-reported terminal idle
     as `done` for a non-interactive custom source (documented in
     spec-capabilities.md); the harness-complete sidebar shape (agent=pi,
     correct non-working terminal state) matches the AC's jcode pattern.
  4. Cleanup: `herdr pane release-agent w3D:p2 --source
     custom:herdr-fleet-pi --agent pi`, `herdr tab close w3D:t2` — pane
     gone, no residue, plush/herdr-fleet fleet lanes untouched.

## Live smoke evidence (local lane run only; nothing committed)

Driver: a throwaway example (deleted before the final commit) that
exercises the adapter library directly — `start` + one `prompt` through
`execute_op_in_worktree` against the sandboxed real pi v0.85.1 in a
disposable worktree under the OS temp dir. Environment allowlist carried
PATH (sandbox bin dir) + HOME only; `DEEPSEEK_API_KEY` was UNSET in the
lane environment (`KEY_FORWARDED=no` printed by the driver) — pi satisfied
the call from its own harness-side credential configuration, which the
adapter never touches, persists, or wires (the adapter contract's
"credentials live in the harness" boundary).

- Task: canary-equivalent INI parser (`inicfg.py` + `test_inicfg.py`,
  python stdlib `unittest` only), spec: comments (`#`/`;`), blank lines,
  sections, first-`=` split, whitespace trimming, case-sensitive keys,
  string values, duplicate-key last-wins, top-level `''` section, and a
  `ValueError` carrying the 1-based line number; >= 14 assertions.
- Result: prompt `status=succeeded`, exit 0, 23.5 s elapsed; worktree
  contained exactly `inicfg.py` + `test_inicfg.py`.
- Acceptance re-run by the lane: `python3 -m unittest test_inicfg -v` ->
  Ran 18 tests, all OK (18 test methods / 26 assertions covering every
  spec rule; acceptance exit 0).
- Transcript: 1,142 bytes captured to the /tmp smoke log; excerpt (head):
  "Done. Two files delivered in ... - **inicfg.py** - parse(text: str) ->
  dict ... comments (even indented) and blank lines ignored ...". No
  secret-shaped text in the transcript (scanned); no key was ever in argv
  (row is flag-only) or any file.
- Process hygiene: after the driver exited, no pi process remained
  (`pgrep` for the sandbox pi path and for `pi --provider` returned
  nothing) — pi exits cleanly, unlike the Hermes canary that lingered.
- pi version probed: `pi --version` -> `0.85.1` (exit 0).
