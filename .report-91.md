## 2. The operator path (what the surface does, key by key)

1. **Board** (`p` = preview): the recorded read model (#83/#90) renders exactly as before; `p` takes the
   *exact selected identity* (`repository#issue`) and requires the presented reviewed run plan to carry that
   item. A selection outside the plan is refused typed (`operator.not_bound`) — the plan is never re-scoped to
   the selection.
2. **Preview**: the reviewed bound-input document is re-rendered through the real preview service
   (`queue_preview::preview_queue`) and re-classified through the same revalidation the daemon runs
   (`queue_executor::revalidate`) — read-only, over the live state. The screen shows the exact 64-hex digest,
   the epoch, the re-observed role revision, the repository/host/harness, the workflow binding, the
   **authorization scope** (boundary phase -> integration/completion branch + caps), the declared step spine
   (resolved or not), every selected item with its eligibility and holds, the presented observations (host
   availability, occupancy, caps, grants, resume) and the top-level holds. Nothing is spawned, no grant is
   issued, nothing is written.
3. **Authorization** (`Enter`, only when at least one selected item is eligible): a separate screen showing the
   exact digest, epoch and role revision again, with an **unchecked** box the operator must set with `Space`.
   `Enter` with the box set is the only key that reaches the submit path (probe P2). Every exit — `b`, `Esc`,
   leaving the screen, a terminal resize, a fresh preview — clears the box (P3, P8). Held work never reaches
   this screen at all (P1): `preview.occupancy_unknown`, `preview.host_unavailable`, `preview.auth_missing`,
   an already-owned item or a missing grant keep the item out of the authorizable set and the surface says why.
4. **Authorize** (the single effect boundary): the digest, epoch and role revision are re-derived ONCE from the
   live state and the CURRENT configuration; a moved digest, epoch or revision refuses typed
   (`refusal.plan.stale` / `refusal.state.epoch` / `refusal.profile.revision`) and submits nothing (pinned by a
   test and, for the epoch, by a probe). The submission goes over the daemon socket as the SAME params document
   the CLI builds (`queue_executor::submit_params`, with the role binding re-observed exactly like
   `queue submit`'s preflight), and the deterministic submission id (`queue_executor::submission_id`) is
   derived *before* the call. The daemon revalidates everything again and commits under its own guard.
5. **Outcome**: **REQUESTED** (what the operator authorized: digest, submission id, selected set, boundary,
   presented observations) and **OBSERVED** (what the daemon reports: epoch, admission counts, per-item status
   and run ids, the daemon's own statement) are separate blocks. A typed daemon refusal is `NOT APPLIED`
   (definite no-effect); a partial send (`client.*` other than a connect failure) or a claim-in-flight
   (`state.claim_reused` / `state.claim_incomplete`) is `UNKNOWN`, the surface states that it will not replay
   it, and the only follow-up is the read-only readback (`r`, `queue.status`). A fresh authorization always
   requires a fresh preview.
6. A typed notice (a hold, a refusal, a readback failure) is rendered on EVERY screen — on the board it
   replaces the footer row, elsewhere it is the line after the heading — so no refusal is silent (P7).
7. The run is **daemon-owned**: the console holds no scheduler, spawns nothing, and writes no state of its own;
   closing the terminal stops nothing (the submission, its admitted run and the single ownership row are the
   daemon's records — proven below), and a reopened surface reads the recorded board and performs no
   submission.

## 7. PENDING INTEGRATION (exact file, exact change, why)

**1. `src/commands.rs` — construct and run the operator console for `canter board`.**
Exact change:
- `parse_board`: accept `--plan PATH` (the reviewed bound-input document — the same material
  `queue submit --request` reads) together with the existing `--config PATH`;
- `execute_board`: after the state store is opened, load the plan (`std::fs::read_to_string` +
  `Val::parse_json`), present it as `tui::operator::PresentedRun::new(<file label>, bound, caps)` with the
  operator's observation axis (`host_available`, `harness_lanes`) and any `grants`/`resume` bindings, then run
  `tui::session::run_operator(&mut tui::operator::OperatorConsole::new(&state, paths.socket_path.clone(), config, Some(presented)))`
  instead of `session::run(&LiveBoard::new(&state))` (`paths.socket_path` is already derived in that function).
Why: this lane's fence is `src/tui/**` + its own tests, so the entry point could not be touched. Without it the
fully-tested operator path is not reachable from the `canter` binary — the same handoff shape #90 needed and
received. Nothing else is needed: the console, the session entry and the presented-run type are public.

**2. Reviewed-plan production (recorded gap, restated for visibility).** The product still has no CLI verb that
renders the #84 preview document or its digest, so an operator cannot yet produce the `--plan`/`--request`
material through the product surface (the pending item #92 already recorded). The operator surface consumes
the reviewed document; it never fabricates one.

   at this head; it is driven by the lane's tests (including a real PTY session) only.
2. **The reviewed plan material is an input.** The surface previews and authorizes the presented document; how
   that document is produced and reviewed by an operator is the recorded #84/#92 gap (section 7.2). Nothing in

4. **Observation attestations are presented, not measured.** `host_available`, `harness_lanes`, `caps`,
   `grants` and `resume` come from the caller (the operator/CLI axis). The surface never guesses them: missing
   values are `unknown` and hold every item instead of admitting one.
5. **`just ci` was run with an out-of-tree cargo target dir** (section 4) — disclosed above; the tracked-tree
   scanners (`check-public-tree.py`, `test-check-public-tree.py`, gitleaks) all ran green over the committed
   head.
6. **Colour-capability PTY matrix not re-run for the operator screens.** The PTY evidence covers the default
   ANSI mode; the mono path of the operator screens is exercised by the fixed-size frame test, and the
   palette-selection logic itself is unchanged from #90 (which has the full PTY matrix).
7. **The PTY assertion on the checked authorization box is deliberately not byte-based.** Ratatui re-emits

   test and the unit tests rather than by the terminal stream (the same "captured bytes != cell grid" rule
