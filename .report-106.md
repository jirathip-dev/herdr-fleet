## 2. Compatibility + state continuity (hard requirement)

Normative contract (single home, linked from README / CHANGELOG / OPERATIONS /
spec-config / skill): `docs/contracts/compatibility.md`, section "Product
rename (issue #106)". Delivered behavior:

1. A **pre-rename state/runtime tree** (`$XDG_STATE_HOME/herdr-fleet/`,
   `$XDG_RUNTIME_DIR/herdr-fleet/`) is **adopted in place** when it exists and
   the `canter/` tree does not: derivation keeps socket and state together,
   nothing is copied, moved, migrated, or deleted, and the daemon opens and
   migrates the existing SQLite state normally. Once a `canter/` tree exists
   it is authoritative; a leftover pre-rename tree is ignored and never
   touched (`src/dirs.rs`: `DIR_NAME` / `LEGACY_DIR_NAME` /
   `adopted_dir_name`).
2. A **pre-rename config** (`$XDG_CONFIG_HOME/herdr-fleet/config.toml`) is
   still discovered when no `canter/config.toml` exists and is read in place
   (`src/config.rs`: `discover_config` / `legacy_config_path`); the new path
   wins when both exist.
3. The **pre-rename binary name** keeps working (alias binary, §1), and the
   **pre-rename crash-point env var** `HERDR_FLEET_CRASH_POINT` is still
   honored next to `CANTER_CRASH_POINT` (debug builds only;
   `src/daemon.rs` `crash_point_requested`, unit-tested for preference
   order).
4. Pre-rename **service units** keep working (their program path is the
   installed binary and the alias above resolves it); new `service *-plan`
   output renders `com.canter.daemon` / `canter.service`. The CLI never
   touches the service manager.
