## What is proven

A fresh VERIFIED delivery of one already-authorized queue run now advances that
submission's cursor **exactly once** and **admits the next eligible approved
issue** of the SAME committed submission — atomically, through the merged #95
driver and the merged #85 admission path, with no conductor prompt, no LLM in
the loop and no new scheduler.

1. **Two-issue auto-advance (library, the real driver path).**
   `tests/queue_advance.rs::a_verified_delivery_advances_the_cursor_once_and_never_twice_across_restart`
   submits a two-issue queue through `State::submit_queue_run` (one
   per-repository slot, so issue 6 is `waiting`), records the reviewed PASS +
   green checks delivery of issue 5 at an exact head, then drives
   `supervision::check_plan` → `State::commit_supervision_check` exactly like
   the daemon does. Asserted: the plan carries the delivery
   (`evidence_id`/head/ordinal), issue 6 becomes `admitted` with a NEW run id,
   its ownership row exists, its own supervision row is `armed` with the SAME
   policy and the SAME approved digest, the delivered run is `done`, and the
   rendered `advance` block reports `cursor_ordinal`/`consumed` 1/`dispatched`
   1 with one immutable row.
2. **Live end-to-end (real daemon, no further request).**
   `tests/queue_advance.rs::the_real_daemon_advances_the_queue_to_the_next_issue_without_another_request`
   spawns the real `canter daemon run`, submits the queue over the socket with
   `--supervise arm` (policy 5 s/60 s), records the delivery through the
   daemon's OWN `apply` mutation path (`review_evidence`, real grant binding,
   real plan), and then only READS: `queue.status` shows issue 6 `admitted`
   with a new run while the client sent no further mutation, `supervision.status`
   shows the dispatched run armed, the delivery row names the recorded head and
   the dispatched run, and further ticks (past the timer interval) leave
   `consumed`/`dispatched` at 1 and the same run id. The journal carries no
   `mutate.harness_start` / `mutate.prompt` / `mutate.merge` and the daemon log
   carries no `spawn`/`supervision.continue`: the continuation is an admission
   record, never a process/harness effect.
3. **Duplicate events and restart never dispatch twice.** The same test replays
   the delivery five more times (`check_plan` → `commit`) and reconciles the
   dispatched run twice: exactly one `queue_advances` row remains, it is
   byte-equal to the row committed by the first consumption (a replay never
   rewrites the cursor), the item→run bindings are unchanged, then the state is
   CLOSED AND REOPENED and the delivery is replayed again after "restart" —
   still one consumed delivery, two runs, item 6 still bound to the original
   dispatched run.
4. **Dependency holds never fabricate completion.**
   `tests/queue_advance.rs::an_unmet_dependency_holds_the_next_issue_with_a_reason_and_never_marks_it_done`
   submits issue 5, issue 6 and issue 7 (`#7` requires `#6`) with two slots, so
   7 waits. After issue 5 is delivered the candidate is issue 7 whose declared
   dependency (issue 6) is admitted but NOT delivered: the row records
   `queue.dependency_unsettled` (message names `#6`), issue 7 stays `waiting`
   with no run, the dependency run is never marked `done`, and nothing is
   dispatched. A replay of the same delivery records the same hold (no
   dispatch). When issue 6 is delivered, the SAME delivery row settles in place
   (`next_instance_id` = issue 7's new run) and issue 7 is admitted — the
   cursor never skipped it.
5. **Existing safeguards stay authoritative.**
   `tests/queue_advance.rs::a_paused_or_invalidated_run_never_advances_its_queue`:
   a run whose safe-boundary pause committed writes NO cursor row at all (the
   delivery is not a delivery while held); after resume the delivery advances;
   a run whose newest recorded verdict is `fail` (a newer row hides any older
   pass) never advances.
6. **The delivery predicate itself.**
   `tests/queue_advance.rs::only_a_reviewed_pass_with_green_checks_at_the_run_pins_is_a_delivery`:
   a pass with every named check `passed` at the run's own pins IS a delivery;
   no evidence, a `fail` verdict, a `pending` check, evidence bound to another
   workflow pin, a run with no committed membership, a paused run and a
   blocked run are all refused. The same predicate (holder) is unit-covered for
   the declared dependency edges:
   `src/state.rs::queue_advance_dependencies_parse_and_unselected_requirements_are_never_met`
   (bare references resolve against the submission repository, foreign
   requirements are dropped — never settled by this queue — and an unreadable
   bound document invents no edge; a `waiting` item and a missing run are never
   "met").

## Trigger, atomicity and idempotency (the delivered contract)

- **Trigger (recorded evidence, never a label):** the newest review-evidence
  row of the run is `pass` with every named check `passed` (the existing
  board/merge-gate evidence contract), bound to the run's own
  `workflow_hash`/`policy_hash` pins, at one exact 40-hex head, with no durable
  hold (paused/pause-requested, `blocked`, human queue, invalidated, terminal
  blocker), no in-flight step claim and a LIVE state epoch. A `done` status
  alone is not a delivery, and neither is a `done` label without passing
  evidence (the #95 rule survives).
- **Atomic:** the delivery consumption, the delivering run's completion
  (`done` — the freed slot is what the next issue is admitted into), the new
  run row, its unique ownership row, its armed supervision authorization, the
  membership item's `admitted` status and the advance row all commit in ONE
  transaction with the reconciliation that recognized the delivery.
- **Idempotent, durable:** `queue_advances` (m0012) holds one row per consumed
  delivery, `PRIMARY KEY (submission_id, delivered_ordinal)` = the delivered
  issue, with the delivered head and evidence id recorded. A duplicate event, a
  replayed check, a crash (SQLite rolls the whole transaction back) or a restart
  can only observe the recorded row; the delivering run's identity is also
  derived deterministically from `(submission_id, work_item)`, so a duplicate
  dispatch is structurally impossible rather than merely unlikely.
- **Reuse, not a second scheduler:** the #95 driver decides (the
  plan carries the intent and the commit re-verifies it under the guard), and
  the #85 admission helper `admit_queue_item_in_tx` — extracted from the
  submission transaction — performs the same ownership/grant/epoch/expiry/
  capacity/overlap checks for the advance, under the SAME approved caps and
  the SAME attested occupancy the submission committed.
- **Only the already-authorized queue:** the candidate is the first `waiting`
  membership item of that submission. No scope expansion, no new issue
  creation, no speculative prerequisite chain; `refused` items are never
  dispatched.

## What is fixture-only / synthetic

- Every identity in the focused suites is synthetic: repository
  `example-org/widgets`, host `host-1`, harness `lane-1`, synthetic 40/64-hex
  revisions and hashes, and provider/model-agnostic role bindings. All state
  lives in per-test temp directories; the owner/paths used by `apply`'s
  topology are inside the test's own temp dir.
- The library-level tests drive the production commit path directly
  (`check_plan` → `commit_supervision_check`) instead of a daemon process; the
  live test covers the full daemon path for the two-issue advance, and the
  dependency-hold/pause scenarios are library-level.
- `queue.dependency_unresolved` is a defensive arm: the committed preview
  classification refuses an item whose requirement is outside the selected set
  at submission time, so the product path cannot produce a `waiting` item with
  an unresolved requirement today. The underlying predicate (an unselected
  requirement is never met) is unit-covered; the end-to-end arm is not driven.

## Unverified / disclosed gaps

- No live *fleet-ops* integration: nothing here touches the live supervisor,
  services, registry or profiles, and no real orchestrator/harness process is
  started by this slice (the continuation is an admission record).
- The inventory of "required CI" checks is whatever the reviewer recorded in
  the evidence row (the existing merge-gate contract: every named check must
  read `passed`); this slice does not invent a required-check list.
- The auto-advance re-applies the caps and the same-harness occupancy
  attestation the submission committed; it never re-observes occupancy (the
  daemon has no adapter observation in this path), so a stale attestation is
  used exactly as approved. Live global/repository/harness-count axes and
  ownership/grants are re-derived under the guard.
- The `done` status of the delivering run is written by this slice (the first
  production writer of `done`): it is what the board's `verified` stage and the
  #95 `completed` classification are derived from. Runs whose delivery is not
  verified keep their existing status untouched.
