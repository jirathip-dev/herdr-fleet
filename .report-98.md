## What is proven

### Restart integrity — the matrix (real process kills, one row per boundary)

Each row kills the real `canter daemon run` child through the existing
debug-only crash hook and then asserts the SAME four properties after the
resume: no duplicate dispatch, no lost queued item, an exactly-once cursor,
and a state consistent with the recorded delivery evidence.

The advance is ONE SQLite transaction (`State::commit_supervision_check` →
`advance_queue_in_tx`): it re-verifies the delivery, completes the delivering
run, dispatches the next approved issue through the SAME shared admission
helper the submission used, and records the cursor row (`queue_advances`, PK
`(submission_id, delivered_ordinal)` — the delivered issue is the idempotency
key). Inside that one transaction the code writes the DISPATCH first and the
CURSOR ROW last; the brief's "between cursor advance and dispatch" therefore
has no separately-observable split state. The two windows between those write
phases (`after-dispatch`, `after-cursor`) plus the post-commit row cover it:

| row | crash point | window the kill lands in | durable state after the abort | after the resume |
| --- | --- | --- | --- | --- |
| a | `queue.advance.after-delivery` | delivery verified by the reconciliation, no advance write yet | evidence row only: 0 cursor rows, 1 run, item 6 `waiting`, delivering run not `done` | boot reconciliation consumes the delivery ONCE: 1 cursor row, item 6 admitted, delivering run `done` |
| b | `queue.advance.during-dispatch` | inside the dispatch (candidate run row written, ownership row not) | identical to (a) — the transaction rolled back | identical: the whole advance re-applied exactly once |
| c1 | `queue.advance.after-dispatch` | dispatch phase finished, cursor row not yet written | identical (rolled back) | identical |
| c2 | `queue.advance.after-cursor` | cursor row written, nothing committed yet | identical (rolled back) | identical |
| d | `queue.advance.after-commit` | the whole advance is durable | 1 cursor row, item 6 admitted under its deterministic `run-` id, delivering run `done` | the restart re-derives the same delivery; the recorded consumption refuses, NOTHING is repeated |

Per-row evidence, all in `tests/restart_pause_continuity.rs`:
- the child dies with signal 6 and its stderr carries
  `crash point "<name>" reached` — the kill provably landed at the NAMED
  boundary, not somewhere else;
- the post-abort durable readback (a fresh `State` on the same DB) holds the
  row-specific state above;
- the resumed daemon reaches `admitted` on its own (no client request);
- a THIRD daemon start commits exactly one fresh check per armed run
  (`class: completed` for the delivering run) while the cursor row stays
  byte-identical, item 6 keeps its single deterministic instance id
  (`run-` + first 16 hex of sha256 over
  `hf-queue-run/v1|{submission}|{work_item}`), `instances` stays 2 and
  ownership stays 2 rows.
- A duplicate dispatch is structurally impossible (the same work item can only
  mint one run id; the item leaves `waiting` inside the same transaction that
  records the cursor row) and is asserted from both the durable rows and the
  rendered `queue.status` document (consumed 1 / dispatched 1 / one row /
  `next_ordinal` 1 / `next_instance_id` = the deterministic id / no hold).

### Pause integrity — the matrix

- The operator pause is durable mid-flight (request + safe boundary, no step
  in flight) with a pending verified delivery. The daemon's own boot check
  records `class: paused`, `eligible: false` (trigger `boot`); a second
  `run.pause` over the wire is refused `refusal.run.control` (one intent).
- Nothing advanced while paused: 0 cursor rows durably, item 6 `waiting`,
  `advance.consumed == 0` / `dispatched == 0` live, and no run is `done`.
- Restart: the hold sticks (the next check is `paused` / ineligible), the
  durable readback is still 0 cursor rows, and `run.status` still carries the
  SAME resume digest.
- ONE explicit `run.resume` (the digest the durable hold carries) advances
  exactly once — consumed 1 / dispatched 1, item 6 admitted under its
  deterministic id, delivering run `done` — and a further restart replays
  nothing.
- The pause matrix runs the PRODUCTION-default policy interval (60 s), so a
  continuation after an explicit resume is bounded by the same recorded
  fallback a live daemon uses (see "Flake analysis" for why).

### Continuation integrity / never a blind spawn

- The only continuation effect is a durable run record. After each advance the
  tests read `journal.tail` (200 rows) and assert no `mutate.harness_start`,
  `mutate.prompt` or `mutate.merge` anywhere, and the daemon log carries no
  `spawn` / `supervision.continue` line. Nothing in this slice starts a
  process, sends a prompt, mutates Git or clears a hold.
- No LLM/polling loop exists in this path by construction: the supervision
  driver is deterministic daemon code over recorded evidence (#95), its module
  guard `the_driver_never_reaches_an_effect_surface` (`tests/supervision.rs`)
  forbids every effect surface, and every time decision takes `now_unix`
  explicitly (no sleep-driven tests).
- A missing/dead operator therefore leaves the run supervised: the resumed
  daemon reconciles from recorded durable state and either performs the ONE
  authorized cursor advance or holds (`paused` / `unknown` /
  `needs-attention`). There is no path that spawns work on its own.
- Continuation state is consistent with the reviewed delivery evidence: the
  delivery is re-verified under the guard from the recorded review row (`pass`
  + every named check `passed` at one 40-hex head, bound to the run's own
  workflow/policy pins and membership item), and the cursor is derived from
  the durable `queue_advances` rows — never from an in-memory cursor.

### Library-level deterministic harness (explicit clock, no sleeps)

- `state_harness_consumes_the_delivery_exactly_once_across_restart_and_a_moved_clock`:
  the crash window itself (delivery durable, no advance) is asserted; the
  reconciliation consumes it once; then FIVE replays at explicit clock offsets
  `+0/+1/+30/+3600/+86400 s` (the whole progress window elapsed) leave the
  consumed row byte-identical and dispatch nothing new; after a reopen (a
  restart) the boot reconciliation recognizes the delivery again and still
  adds nothing.
- `state_harness_paused_hold_survives_reopen_and_the_resume_advances_once`:
  the paused plan carries no delivery (`advance: None`), the commit records
  the hold, the reopen (restart) check is still `paused`, and ONE resume then
  advances exactly once with an immutable row afterwards.

## What is fixture-only / synthetic

- All identities are synthetic (`example-org/widgets`, runtime-built
  `run-`/`gr_`/`ik_` values); no real repository, host, harness, provider or
  credential is involved and no provider call exists anywhere in this path.
- The kills use the existing debug-only crash hook (`CANTER_CRASH_POINT`,
  documented in `docs/contracts/compatibility.md`); release binaries ignore
  it, so the matrix cannot be weaponized against a running fleet.
- No live supervisor, service, registry or profile was touched; no
  main/release/production action; no real cutover.

## Flake analysis and disclosed findings

1. **`just ci` / `just test` on a saturated host (the known load-skew class).**
   Two earlier aggregate runs failed with exit 101 and EXACTLY one failing test
   — `daemon_rpc::non_draining_subscriber_is_disconnected_under_backpressure`,
   `client.read: Resource temporarily unavailable (os error 35)` — the 15 s
   daemon-client read deadline missed under load (the suite took 118–186 s
   instead of ~10 s; 1-min loadavg 196–380). Classification evidence:
   (a) `tests/daemon_rpc.rs` is byte-identical to the base
   (`git diff origin/staging..HEAD -- tests/daemon_rpc.rs` empty);
   (b) that target exercises no queue/supervision write path
   (`queue.submit|queue.status|supervision.status|commit_supervision_check|admit_queue_item`
   → 0 matches), so none of the added boundaries are on its path;
   (c) the same target passes in isolation at this head (13 passed, exit 0);
   (d) a real green `just test` (exit 0) was obtained at the immediately
   previous head (the last amend changed only the new test file) and the final
   aggregate `just ci` at the delivered head runs the `test` step green
   (exit 0) together with every other recipe. The host ran other lanes' work
   throughout (four `vitest` workers, two `chrome-headless-shell` processes,
   an iOS simulator, `herdr`) plus ~120 LEAKED IDLE `canter daemon run`
   processes from long-merged lanes (issue-78 ×24, issue-79 ×19, issue-86 ×15,
   issue-77 ×12, hf-97 ×9, issue-95 ×8, issue-91 ×9, …; the oldest from the
   previous day). They are NOT this lane's processes and were not killed (host
   reclamation is orchestrator territory) — reported as a host-hygiene
   finding.
2. **One real flake in the first cut of the pause matrix (found by the
   under-load leg, fixed).** With an artificial 1-hour policy interval, one
   under-load run failed: 30 s after an explicit `run.resume`, the durable
   readback still showed 0 cursor rows / item 6 `waiting`. Forensics on that
   run's store: `checks=4`, `last_check_class=paused`,
   `last_check_trigger=control`, `next_check_unix` = +3600 s, no pending
   trigger and no cursor row; the instance was already resumed (`paused=0`),
   the delivery evidence intact, and the event cursor had reached the resume's
   outcome event. So the continuation was DELAYED, not lost or duplicated: the
   last committed check read a still-pre-effect snapshot (the daemon journals
   and publishes a mutation's INTENT before its effect), consumed the wake
   slot, and scheduled the next check one interval out; the wake fold's
   intent/outcome accounting (intent action → wake class `control`, outcome
   action → `completion`) is the open detail. Under the production-default
   policy the consequence is a bounded delay (≤ the recorded
   `check_interval_secs`), never a lost or repeated action. The pause matrix
   now runs the PRODUCTION-DEFAULT interval (60 s) and bounds the post-resume
   advance by `interval + slack`, instead of hanging a hard requirement on an
   artificial 1-hour interval.
3. **`test-build-archive.py` showed NO load artifact**: green in isolation
   (222 s cold, 6 s warm) and green while two acceptance-suite loops ran
   concurrently.
