## 1. Delivered

1. **`canter board` reaches `run_operator`/`OperatorConsole`.** `parse_board` now accepts, besides
   `--config PATH`, the presented run: `--plan FILE` (the reviewed bound-input document — the same
   material `queue submit --request` reads) plus the attested observation axis `--caps G/R/H`
   (required with `--plan`), `--host-available yes|no|unknown`, `--harness-lanes N|unknown`,
   `--grant REF=GRANT_ID`, `--resume INSTANCE=DIGEST`. `execute_board` loads the document, builds
   `tui::operator::PresentedRun` and runs `tui::session::run_operator(&mut OperatorConsole::new(
   &state, paths.socket_path.clone(), config, presented))` over the daemon state store. Without
   `--plan` the surface stays the read-only board (no run presented; a preview request is the typed
   `operator.plan` notice) — the console, not a UI scheduler, owns every effect boundary, and it
   consumes the same typed services the CLI uses (`queue_preview::preview_queue`,
   `queue_executor::revalidate`, `queue.submit` over the derived socket).
2. **Real plan producer (the recorded #92 plan-production gap): `canter queue preview`.** The new
   subcommand renders the effect-free `hf-queue-preview/v1` document through the real #84 preview
   service over the recorded state store, re-observes the repository identity + workflow pin +
   reviewed role binding from configuration (never free text), declares the doctrine spine with
   every step's parameters resolved, derives the boundary capability set from that spine, and
   writes the exact bound-input document to `--out FILE`. Its sha256 is the digest
   `queue submit --confirm-digest` and the operator authorization bind. Exit codes: 0 ok, 1 no
   state store / write failure, 2 usage, 4 unsupported configured workflow pin, 5 config.
3. **`src/plan.rs`**: `queue_run_steps` (the doctrine queue-run spine producer: run-wide checkout /
   harness_start plus one resolved step per selected issue, ids `p<index>-<issue>`) and the now
   public `doctrine_workflow_hash` the producer reuses (one derivation, never a second copy).

No other product surface was touched. `src/tui/**` is byte-unchanged (the operator surface and the
session entry were already public): nothing is pending there. `src/state.rs`, `src/daemon.rs`,
`src/queue_executor.rs`, `src/supervision.rs` are untouched (the #96 fence), as are the live
supervisor/services/registry/profiles, `main`/release/production, and the live fleet.

## 3. What is fixture-only (disclosed plainly)

- Synthetic identities only: `example-org/widgets`, `host-1`, `lane-1`, `run-seeded-0001`,
  `provider-a`/`model-a` in the per-test temp config; nothing lives in a host state dir.
- The seeded state (one active `hf-grant/v1`, one recorded run that already left the owned set)
  is a fixture written through the library's real `State::issue_grant` / `start_instance` APIs,
  the same seed `tests/tui_operator.rs` uses. No CLI verb issues grants in this slice.
- The reviewed plan document is produced by the REAL `queue preview` command, never hand-assembled;
  the daemon, the socket, the terminal and the submission are real.
- Observation attestations (`--host-available yes`, `--harness-lanes 0`, `--caps`) are the
  operator's presented facts, exactly the axis `queue submit` presents; the surface never measures
  or infers them (defaults are `unknown`, which holds work).
- The submission is admission only: no workflow step executes and no harness process is spawned
  (the daemon's own statement travels with the committed document). No live fleet, supervisor,
  service, registry or profile was involved.

## 4. Semantics the wiring preserves (point 3 of the brief)

- **Keyboard/back/cancel can never authorize; authorization is a separate explicit action.** The
  console is unchanged and its tests still pass at this head (`tests/tui_operator.rs`, 5 tests in
  `just ci`): `Space` sets the authorization box, only the authorization screen's `Enter` reaches
  the submit path, and every other key/back/quit/resize clears or never sets it. The new entry
  point feeds that console; it adds no shortcut.
- **Requested vs observed effects are both visible; unknown stays unknown.** The captured outcome
  screen shows `REQUESTED (what the operator authorized)` and `OBSERVED (what the daemon reports)`
  as distinct blocks; an unconfirmed attempt stays `UNKNOWN` and its only follow-up is the
  read-only `r` readback (operator-module tests).
- **Closing the terminal does not stop daemon work; reopening reads real state and never replays.**
  Proven in this lane's PTY test: the board process exits, the submission survives in the daemon,
  a separate `canter queue status` process reads it back, and the state store holds exactly one
  ownership row (no replay). A preview request without a presented run is refused typed
  (`operator.plan`) and writes nothing.

2. **The declared queue spine is bounded at 32 steps** (`queue_preview::STEPS_MAX`, six steps per
   selected issue): `queue preview` refuses a selection larger than five issues with a typed
   `usage.queue_steps` rather than emitting a document the preview/submission would refuse.
   Multi-issue operation beyond that bound (or a distinct per-issue spine shape) is a follow-up
   design decision, not a hidden truncation.

   declared step labels (id + kind), so the queue spine's derived hash differs from the hf-plan
   spine's for the same workflow, and a configured pin is what makes a grant's `workflow_hash`
   agree with a submission's (the documented `docs/OPERATIONS.md` example is unchanged; no docs
   were edited). Any no-pin grant producer must derive with the same public function.
